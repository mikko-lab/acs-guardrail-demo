## Summary
v0.6.0 adds an opt-in approval–permit lifecycle, makes both modes run the request they verified, and ships a runtime-test mutant gate for the lifecycle:
- **Approval–permit lifecycle (permit mode, G3/G4).** Permit mode is opt-in, with `{ lifecycle: "permit" }`; legacy mode stays the default.
  - **No tool call in `process()`.** In permit mode, `process()` creates a lineage and never starts a tool:
    - a Guardian `ASK` gives a `pending` lineage;
    - `ALLOW` gives an `approved` one, with approver `policy`;
    - `DENY` gives no lineage.
  - **Separate steps:**
    - `approve()` / `reject()` take a human `ApprovalGrantV3` that signs the lineage, the request digest and the authority fingerprint;
    - `issuePermit()` issues one permit;
    - `start()` takes a fresh signed request and compares it with the lineage field by field.
  - **Single use.** The permit is consumed only at the start effective point, immediately before the tool call. Of concurrent or re-entrant starts, exactly one runs. A start that passed that point keeps the permit consumed, even if the tool fails.
  - **Final fences.** Every operation (create, approve, issue, start) re-checks revocation and chain validity at its own final fence after its last callback. A revocation covers pending approvals and unused permits, and they are listed in the receipt. Approval and permits never restore revoked or invalid authority.
  - **Bound authority.** The execution is always bound to the lineage's authority. All transitions share one sequence with revocations.
- **The verified request is the request that runs, in both modes.** `process()` takes one runtime-owned, deep-frozen copy of the request at entry, before any check. The following all read only that copy:
  - signature, replay and capability checks;
  - the Guardian decision;
  - the bindings or the pending action;
  - the tool call.
- **Fix: legacy request-mutation TOCTOU.** The defect was present since `a9deab6`: in legacy mode, a callback after the checks could rewrite the caller's request object (the capability provider, the audit sink, or the Guardian, which is handed the request). The rewritten tool, arguments, session or request id then ran, or became the pending action that `resolveApproval()` approved and ran. Now the caller's object is never read again. A Guardian write attempt makes `process()` fail before anything runs or is pending (`docs/legacy-request-snapshot.md`).
- **Lifecycle mutant gate.** `npm run mutants:lifecycle` checks that the lifecycle tests separate each named check of plan §8.2 (M53–M71), under a strict whole-run rule.

## Compatibility
- **Legacy mode remains the default.** Permit-mode APIs throw `LifecycleModeError` in legacy mode, and `resolveApproval()` throws it in permit mode.
- **Request snapshot, both modes.** Results for unmodified requests are unchanged. The documented changes are:
  - a request that is not a JSON value (a cycle, a `BigInt`) is rejected at entry (`Validation Error: request must be a JSON value`);
  - a callback that writes to the request it is handed makes `process()` fail;
  - nested argument values handed to a tool are frozen, so a tool that writes into one ends as a tool failure (`tool_execution_failed`).
- **Types.**
  - `GuardedExecutor` is generic in its mode (`GuardedExecutor<M extends LifecycleMode = "legacy">`). Legacy code keeps the unchanged `ProcessResult`.
  - New: `ApprovalGrantV3` and `ApprovalGrantVerifier.verifyV3()`, `LifecycleDeniedError` and `LifecycleModeError`.
  - `RevocationStage` gains `issue`, and `AuthorityRevokedError` gains `check` (`early` / `final`).
  - In permit mode, the revocation receipt adds `pending_lineages`, `approved_lineages` and `unused_permits`.
- **Audit and OCSF.**
  - New event types `approval_granted`, `permit_issued`, `permit_expired` and `lifecycle_operation_denied`.
  - `lineage_id` (and `check`) on the existing events of the permit-mode paths.
  - The OCSF allowlists list exactly these keys.

## Lifecycle mutant gate
- **Coverage.** 26 manifest entries: M53–M71 of the approved plan and its named variants.
  - **20 distinct patches**, which are 20 mechanisms.
  - **6 variants** (M58-i/iii, M61-i/iii, M62-i/iii). A variant has its main entry's patch (an identical run) and reads another witness. It is counted separately and is not an independent mechanism.
  - The manifest is version 4, pinned by SHA-256. Each entry pins its patch, the witness values, the accepted errors and the collateral observations exactly.
- **Evidence kinds**, reported separately and never merged:
  - **Containment** (a tool runs that must not): M53, M54, M58, M59, M60, M64, M66.
  - **Lifecycle** (a wrong approval, permit or lineage transition; no tool runs): M61, M62, M63, M67, M68, M69, M70-create.
  - **Availability** (an allowed action is denied): M65.
  - **Check point only** (the denial moves, the action stays denied): M57, M70-start and the six variants.
  - **Component only** (no production-path witness): M55, M56, M71.
- **Claim limits.**
  - **M58** shows snapshot continuity only. It does not show the use of a revoked or expired authority, nor an authority substitution.
  - **Lifecycle-only entries.** That a later fence still denies the start is inferred, not run.
  - **Beyond the claimed kind.** Labels that change outside an entry's claimed kind are reported and not counted, for example M67's tool call.
- **Gate driver.** A named witness must fail with exactly its rebuilt `WitnessAssertionError`, and any additional failure is technical. These are technical failures (exit 2):
  - a witness-log entry that cannot be bound to exactly one test;
  - a patch that does not take effect;
  - an unknown `--only` id.

  Regressions RL1–RL24 check the gate itself. The expected values come from a precheck run, so a detection is reproducibility evidence.

## Limitations
- **Masked mutants.** M70 at approve and issue is masked: with the patch applied, every test still passes. They are recorded gaps, not evidence.
- **Component gaps.** M55 (session and agent comparisons at start) and M71 (the execution's authority source) have component evidence only. M56's tenant comparison is structurally masked on the production path.
- **Gate limitations A5–A9** (`docs/mutant-gate.md#known-limitations`):
  - A5: a collateral pin binds the assertion text, not its position.
  - A6: loose assertions in tests that are not witnesses weaken the whole-run rule.
  - A7: the witness-log encoding is lossy.
  - A8: kinds and parts are the manifest's own claims.
  - A9: the hash proves the manifest's integrity, not its registration before the run.
- **Tenant and ancestor gate debt.** These manifests are not on the strict whole-run rule, and their errors are matched by prefix. The new binding, witness-failure, patch and `--only` rules apply to them.
- **Unchanged from v0.5.0.** Revocation is in memory, for one executor in one process. Cancellation is cooperative. The commit fence covers only `ctx.commit()`.

## Evidence and its limits
- **Tests.** `npm run verify` passes: typecheck, build, and 33 Jest suites with 774 tests, on Node 22 and 24.
- **Mutant gates.**
  - Lifecycle 26/26 detected.
  - Regressions RL1–RL24 as required.
  - Lifecycle witnesses deterministic over 3 identical runs.
  - Tenant 19/19, ancestor 25/25, and R1–R4 pass.
- **Not an eval pass.** This release is runtime-own evidence. It does not claim to pass the `agent-control-evals` revocation contract. The eval repository's implemented baseline is still 17/27 with K = 43 and exit 3. The eval-side lifecycle mutants (plan §8.1), the SUT pin and the adapter extension are separate, later work.
- **No conformance claim.** No full ACS conformance or certification claim.
