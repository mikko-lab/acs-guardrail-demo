## Summary
v0.5.0 adds explicit authority revocation and containment to the runtime:
- **Authority revocation (A1).** `revoke()` revokes a capability or a session. The revocation is enforced at the request, approval, start and delivery boundaries.
- **Cooperative containment (A2).** Every call runs as a managed execution. A revocation requests its cancellation, and a commit fence guards `ctx.commit()`. Each execution produces exactly one observed terminal.
- **Tenant scope (package 1a).** Tenancy mode is opt-in.
  - Tenants come from issuer-signed `CapabilityGrantV2` grants; the tenant is read only from the verified grant.
  - Each runtime session is bound to one tenant, and a grant of another tenant for that session is rejected (`session_tenant_conflict`).
  - `revoke({ scope: "tenant", tenant_id })` is enforced at every check point and cancels the tenant's running executions. Other tenants are unaffected.
- **Ancestor chains and descendant revocation (package 1b).** Chains exist only in tenancy mode.
  - A grant may name its parent by `capability_id` and content fingerprint. The provider supplies the complete issuer-signed chain, at most 8 grants, leaf included.
  - Every chain member is verified: structure, signature, validity, both link directions, a single tenant, and attenuation (the child's tools are a subset of the parent's, and its validity window lies inside the parent's).
  - A wrong chain is rejected before any binding, the Guardian decision, a pending approval, a permit, an execution or the tool call, and it leaves nothing bound.
  - A capability revocation of an ancestor covers its descendants (`ancestor_revoked`) at every check point and in the cancellation fan-out, also when the ancestor was revoked before its first use. It never covers parents or siblings.
- **Fix: audit metadata no longer aliases the authority.** In the unreleased package-1b development head, an audit sink could empty the `capability_verified` ancestor list and so remove the execution's ancestor binding before start. The verified ancestor ids are now frozen before the first callback, and audit sinks receive copies. Regressions C6.01–C6.03 cover this, and mutant M42c restores the aliasing to show that the regressions detect it.

## Compatibility
- **Legacy mode remains the default.** A verifier without `{ tenancy: true }` accepts only version 1 grants, as before. In this mode the following are now rejected:
  - a version 1 grant that carries `tenant_id` or `parent` (`MALFORMED_GRANT`); before this release these fields were ignored;
  - a version 2 grant;
  - a chain envelope.
- **Tenancy mode** accepts only version 2 grants with `tenant_id`; there is no default tenant and no mixed mode. A version 2 grant with `parent` is accepted only together with its verified chain.
- **Approval** re-checks the original authority (revocation, current validity, the provider's current answer). For a chained grant, the provider's chain must equal the snapshot member by member.
- **Types.**
  - `CapabilityGrantVerifier.verify()` returns `CapabilityGrantV1 | CapabilityGrantV2`.
  - `RevocationTarget`, `RevocationReason` and `CommitBlockReason` gain tenant and ancestor variants.
  - `ExecutionSnapshot` and `ExecutionTerminal` gain optional `tenant_id` and `ancestor_capability_ids`.
  - `ToolImplementation` takes an optional execution context.
  - The audit sequence and the OCSF allowlists gain the new revocation and execution events and fields.

## Limitations
- Revocation is in memory, for one executor instance in one process. It is not persistent, not distributed, and lost on restart.
- Cancellation is cooperative. A revocation does not stop a running tool, and an acknowledged cancellation is not termination.
- The commit fence covers only `ctx.commit()` on the runtime's in-memory managed state. Effects outside it (network, external transactions, non-cooperating code, unregistered background work) are not prevented, and a revocation does not undo an earlier commit.
- Tenant scope uses one issuer key and one executor for all tenants. Tenants are not separate trust domains. Holder-to-holder delegation is not provided.

## Evidence and its limits
- **Tests.** `npm run verify` passes: typecheck, build, and 30 Jest suites with 628 tests on Node 22 and 24.
- **Mutant gates.** The runtime-test mutant gates detect every named mutant with its pre-named witness and exact values: tenant 19/19, ancestor 25/25. The gate's own regressions R1–R4 pass.
- **M33.** The tenant field of the capability fingerprint has component evidence only (`component_check_point`). No production-path witness separates it from the kept safeguards.
- **M42a.** It covers re-resolution of the chain at the commit fence only. The delivery checks and the cancellation fan-out use the same start-time binding, but they have no re-resolution mutant of their own.
- **Check-point evidence only.** M40, M47 and M48 are check-point evidence; their kept safeguards still contain the effect. Ancestor expiry between request and approval has no isolated witness.
- **Not an eval pass.** This release is runtime-own evidence. It is not a pass of the `agent-control-evals` revocation contract. The eval-side corpus, the supplement cases, the adapter extension and the SUT pin are separate, later work.
- No full ACS conformance or certification claim.
